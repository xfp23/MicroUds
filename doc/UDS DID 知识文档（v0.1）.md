# UDS DID 知识文档（v0.1）

面向 MicroUds 的 DID 模块设计 · 只整理知识与设计问题，不含实现代码 · 2026-10-23

## 0. 阅读说明

- 标记约定：【标准】来自 ISO 14229-1（不同版本表述有差异，落地以你们依据的版本和 OEM 规范为准）；【实践】业界常见做法，各 OEM 可能不同；【建议】我的设计建议，可以不采纳。
- 范围：DID 的概念、0x22 / 0x2E 的细节、0x2C / 0x2A / 0x2F / 0x24 与 DID 的关系、DID 模块设计时必须回答的问题。RID（0x31）另行整理。
- 第 9 节标注了你贴的那篇文章里几处需要谨慎对待的结论。

## 1. 先回答你的问题：会话和安全权限是跟服务走，还是每个 DID 独立？

**结论：两层都有，必须分开配置，最终能否访问 = 服务级条件 AND DID 级条件。**

1. **服务级**（0x22、0x2E 本身）：决定这个服务在当前会话下是否存在，是粗粒度的闸门。
2. **DID 级**：每个 DID 独立拥有自己的会话条件和安全条件，并且**读和写分别配置**。

### 为什么不能只用服务级

- 同一个 0x22 下，VIN（F190）可能默认会话就能读，而某个标定 DID 要扩展会话 + 安全等级 1 才能读。
- 同一个 0x2E 下，有的 DID 扩展会话 + 等级 1 可写，有的要编程会话 + 等级 2，有的根本是只读。
- OEM 的诊断规范里，DID 表通常就是逐 DID、逐读写列出：DID、名称、长度、读-会话、读-安全、写-会话、写-安全、数据格式。你的配置结构最好能和这张表一一对应，将来 MicroRuntime Studio 才能直接从表生成配置。

### 服务级应该怎么配

- 服务级条件应该是它下面所有 DID 条件的**并集（最宽松者）**：0x22 的会话 = 所有可读 DID 的会话并集；0x2E 的会话 = 所有可写 DID 的会话并集；安全通常设为「无」，因为要不要解锁取决于具体 DID。
- 如果服务级比并集更严，会把本来允许的 DID 误挡在外面，而且返回的 NRC 也不对（见下表）。
- 【建议】服务级条件由 DID 表自动推导（生成器算并集），不要手工再填一遍，避免两处不一致。

### 不同层级失败时的 NRC

| 情形 | 常见 NRC | 说明 |
| --- | --- | --- |
| 服务在当前会话不可用 | 0x7F | 服务级判断 |
| DID 不存在 | 0x31 | 【标准】requestOutOfRange |
| DID 存在，但当前会话不允许读/写 | 0x31 | 【实践】多数规范按「当前会话不支持该 DID」处理，个别 OEM 用其他码，以规范为准 |
| 0x2E 写只读 DID | 0x31 | 【实践】 |
| DID 需要安全解锁但未满足 | 0x33 | 【标准】0x22 中只要有一个 DID 受保护且未解锁就返回 0x33 |
| 车速、挡位等工作条件不满足 | 0x22 | 属于「条件检查」，不是会话也不是安全 |

### DID 级配置的几个细节

- **读写分离**：读一份、写一份。用「会话条件为空 = 不可读 / 不可写」表达只读，比另外加一个只读标志更统一。
- **安全条件的表达方式**（指定等级 / 不低于某等级 / 位掩码）要和服务表保持同一套规则、同一个判定函数，否则服务级和 DID 级会出现判断不一致。
- **继承还是显式**：DID 不填时继承服务级默认，配置少，但「默认值」会悄悄放宽权限；显式填写更啰嗦也更安全。【建议】DID 级权限必须显式配置。
- 会话切换会重新锁定安全访问，所以安全条件**每个请求都要重新判断**，不能缓存「某 DID 已授权」。
- **动态 DID**（0x2C）读取时，要对每个源 DID 的读权限再检查一遍；动态 DID 自身的权限不能比源 DID 宽松，否则可以借动态 DID 绕过安全。
- **多 DID 请求**：每一个 DID 都要做权限检查；遇到安全不满足的 DID，整条请求回 0x33，不返回部分数据。
- 服务级与 DID 级最好**只在一处判断**，约定好谁产生哪个 NRC，避免重复判断后返回不一致的码。

## 2. DID 基础

### 2.1 标识符与数据记录

- DID 固定 2 字节，报文里高字节在前：`did = (b1 << 8) | b2`。
- DID 只是标识符；它对应的**数据记录（dataRecord）长度、字节序、编码、缩放都由 DID 的定义决定**。DID 是 2 字节不代表数据也是 2 字节。
- **报文里没有通用的长度字段**：0x22 响应里 DID 后面直接跟数据，0x2E 请求里 DID 后面直接跟数据。接收方只能根据 DID 的定义知道数据有多长。

### 2.2 DID 区间（只记住与实现有关的几段）

| 区间 | 用途 |
| --- | --- |
| 0x0100–0xEFFF 中的大部分 | 车厂自定义，其中夹杂若干法规保留区间 |
| 0xF100–0xF1FF | 标识类 DID（软硬件号、VIN、日期等） |
| 0xF200–0xF2FF | 周期 DID（0x2A 使用） |
| 0xF300–0xF3FF | 动态定义 DID（0x2C 使用） |
| 0xF400–0xF8FF | OBD 相关 |
| 0xFA00–0xFAFF | 气囊 / EDR / 安全系统 |
| 0xFD00–0xFEFF | 系统供应商自定义 |
| 0xFF00 起 | UDS 版本等少数标准项 |

细分区间请以标准附录为准，不要凭记忆硬编码。模块里真正需要的判断只有：这个 DID 是否落在动态区间 / 周期区间。

### 2.3 常见的标准标识类 DID（长度和编码由 OEM 规定）

| DID | 含义 |
| --- | --- |
| F180 / F181 / F182 | 引导软件 / 应用软件 / 应用数据标识 |
| F183 / F184 / F185 | 引导 / 应用软件 / 应用数据指纹 |
| F186 | 当前诊断会话（1 字节，值为会话编号） |
| F187 | 车厂备件号 |
| F188 / F189 | 车厂 ECU 软件号 / 软件版本 |
| F18A | 系统供应商标识 |
| F18B / F18C | ECU 制造日期 / 序列号 |
| F190 | VIN |
| F191 | 车厂 ECU 硬件号 |
| F192 / F193 | 供应商 ECU 硬件号 / 硬件版本 |
| F194 / F195 | 供应商 ECU 软件号 / 软件版本 |
| F199 / F19D | 编程日期 / ECU 安装日期 |

F186 的值就是内核自己的会话状态，是很适合做成内核内置 DID 的一个例子。

### 2.4 长度：固定、变长、自描述

- **固定长度**：最简单，请求和响应都能校验长度。
- **变长**：写入时长度可以由整条请求长度推出来；但**多 DID 的读响应里没有分隔符**，诊断仪只能依靠 DID 定义（ODX 等）知道每段多长。所以变长 DID 要么只允许单独读取，要么数据格式自描述（带长度前缀或结束符，需 OEM 约定）。【建议】DID 表里标明是否变长，变长 DID 声明最大长度，读取时回报实际长度。
- 字符串类（VIN、编号）通常固定长度，不足补填充字符，由 OEM 约定。

### 2.5 数据来源

| 来源 | 读 | 写 | 要注意 |
| --- | --- | --- | --- |
| Flash 常量 | 直接读 | 不可写 | 版本号、硬件号 |
| RAM 变量 | 直接读 | 直接写 | 多字节一致性（读写被打断） |
| 实时计算 / 采样 | 回调现算 | 通常只读 | 回调不能阻塞 |
| NVM（EEPROM / Flash 模拟） | 可缓存 | 需要持久化，可能慢、可能失败 | 掉电一致性、写失败的 NRC |

## 3. 0x22 ReadDataByIdentifier

### 3.1 报文

- 请求：`22 [DID_H DID_L] ×N`；响应：`62 [DID_H DID_L 数据] ×N`，顺序与请求一致。
- 例：读 F190 和 1234（2 字节）：请求 `22 F1 90 12 34`，响应 `62 F1 90 <17字节VIN> 12 34 AA BB`。

### 3.2 处理阶段

1. 长度检查：DID 部分必须是 2 的整数倍且至少一个 → 否则 0x13。
2. DID 个数检查：超过模块允许的最大个数 → 0x31（【标准】把「超过最大个数」列为 0x31 条件之一）。
3. 逐个 DID：查找、会话条件、安全条件、工作条件。
4. 汇总响应总长度，超过响应缓冲 → 0x14。
5. 逐个读取并拼装响应。

第 1–4 步都不应该有副作用；真正读数据放在最后，避免读了一半才发现整条要失败。

### 3.3 必须由你选定的策略

| 议题 | 选项 | 说明 |
| --- | --- | --- |
| 部分 DID 不支持 | 整条 0x31 / 跳过不支持的 | 【标准】规定了「全部都不支持」时的 0x31，部分不支持时的行为各 OEM 不同。做成配置开关，写进测试 |
| 同一 DID 重复出现 | 允许 / 拒绝 | 允许则响应里重复出现 |
| 功能寻址 | 允许 / 忽略 | 0x22 多数规范限制功能寻址；不允许时应静默 |
| 读取一致性 | 逐个读 / 取快照 | 多个 DID 之间的数据可能在读取间隙变化，要求一致时需加锁或同周期采样 |
| 读取较慢 | 同步 / 0x78 | 从 NVM 读取很慢时可以走 ResponsePending |

## 4. 0x2E WriteDataByIdentifier

### 4.1 报文

- 请求：`2E DID_H DID_L 数据…`（一次一个 DID）；响应：`6E DID_H DID_L`，不回传数据。
- 数据长度 = 请求总长 − 3。固定长度 DID 必须严格等于定义长度，否则 0x13。

### 4.2 NRC 与校验分层

| NRC | 场景 |
| --- | --- |
| 0x13 | 长度不对（过短、过长、固定长度 DID 不相等） |
| 0x22 | 工作条件不满足 |
| 0x31 | DID 不存在 / 只读 / 当前会话不允许；数据取值越界 |
| 0x33 | 需要解锁而未解锁 |
| 0x72 | 写入失败（GeneralProgrammingFailure），例如 NVM 写失败 |

校验分两层：**协议层**（DID、长度、会话、安全）由模块统一做；**数据层**（取值范围、业务状态、是否真的写成功）由 DID 的回调做。NRC 优先级请对照标准及 OEM 规范，选定一种顺序后写进测试，不要在不同分支里各返回各的。

### 4.3 写入语义与可靠性

- **「写成功」的含义**必须定义清楚：数据已被接受，还是已经持久化？涉及 NVM 的 DID 通常要写完并确认后才回 0x6E。
- NVM 写入可能很慢：需要异步（先回 0x78，完成后再回最终响应），内核的 pending 机制要能支撑。
- **掉电一致性**：多字节 DID 写到一半掉电会得到半新半旧的数据。常见做法是双缓冲 + 校验 / 版本号，写完整后再切换。
- **生效时机**：有的 DID 写入后需要复位才生效，应用层要知道。
- **特殊写规则**：只读 DID；一次性可写 DID（出厂写入后锁定，如 VIN）；写入次数限制；指纹类 DID 在编程流程中写入。这些属于 DID 的属性，不是服务级规则。
- **动态定义的 DID 通常不能作为 0x2E 的目标**（标准对 0x2E 有此说明，具体措辞请核对版本）。
- 【建议】DID 是数据，RID 是动作：写一个 DID 会触发标定、擦除等业务动作时，应改用 RID，而不是在写回调里做事。

## 5. 与 DID 相关的其他服务

### 5.1 0x2C DynamicallyDefineDataIdentifier

用于运行时定义一个「动态 DID」，把已有数据组合起来，之后用 0x22 读取。它定义的是**数据从哪里来、取多少、怎么排列**，不是一个可以随意写入的新变量。

| 子功能 | 请求格式 | 说明 |
| --- | --- | --- |
| 0x01 defineByIdentifier | `2C 01 DDDID(2) [源DID(2) 位置(1) 长度(1)] ×N` | 从已有 DID 的数据记录里取片段。位置的起算方式【标准】从 1 开始，请核对版本 |
| 0x02 defineByMemoryAddress | `2C 02 DDDID(2) ALFID(1) [地址 长度] ×N` | ALFID 高半字节 = 长度字段字节数，低半字节 = 地址字节数；地址和长度宽度由它决定，不能写死 |
| 0x03 clear | `2C 03 [DDDID]` | 清除指定动态 DID；很多实现里省略 DDDID 表示清除全部，请按所用版本确认 |

- 正响应：`6C <子功能> [DDDID]`。
- 动态 DID 必须落在动态区间（F300–F3FF 一带）。
- 需要限制：最大动态 DID 个数、每个 DID 的片段数、总长度；创建时就累加并检查。
- **按地址定义**会让诊断仪读任意内存：量产建议默认关闭，或者只允许明确配置的可读内存区间；必须检查地址 + 长度的整数溢出、区间是否可读、会话和安全等级。
- 读取动态 DID 时对每个源 DID 重新做读权限检查（第 1 节）。
- 同一 DDDID 再次定义是覆盖还是追加，不同版本 / OEM 做法不同，需要你拍板。
- 动态定义通常在复位或回到默认会话后失效，是否掉电保存也需要决定。

### 5.2 0x2A ReadDataByPeriodicIdentifier

请求 `2A <模式> [周期DID低字节]…`，周期 DID 取自 F200–F2FF 区间，只用低字节。模式通常为 01 慢 / 02 中 / 03 快 / 04 停止。周期数据一般由 ECU 主动发出，常使用独立的非 ISO-TP 报文，与 MicroIostp 的接口要单独设计。

### 5.3 0x2F InputOutputControlByIdentifier

请求 `2F DID(2) 控制参数(1) [控制状态] [使能掩码]`。控制参数通常为：00 归还控制权给 ECU、01 恢复默认、02 冻结当前状态、03 短期调整。要点：会话和安全要求通常很严；必须保存被接管状态；会话切换、S3 超时和复位时必须归还控制权。DID 在这里是控制对象的标识，语义是「控制」而不是「数据」。

### 5.4 0x24 ReadScalingDataByIdentifier

请求 `24 DID(2)`，返回该 DID 的数据类型、单位、缩放公式等描述。使用较少，放在最后考虑。

## 7. NRC 速查（0x22 / 0x2E / 0x2C）

| NRC | 0x22 | 0x2E | 0x2C |
| --- | --- | --- | --- |
| 0x12 | — | — | 子功能不支持 |
| 0x13 | 长度非 1+2N | 长度不对 | 长度或格式不对 |
| 0x14 | 响应超缓冲 | — | — |
| 0x22 | 工作条件不满足 | 工作条件不满足 | 条件不满足 |
| 0x24 | — | — | 顺序错误（视规范） |
| 0x31 | DID 不支持、超过最大个数 | DID 不支持、只读、取值越界 | 源 DID 不支持、位置或长度越界、超过上限 |
| 0x33 | 有 DID 需要解锁 | 需要解锁 | 需要解锁 |
| 0x72 | — | 写入失败 | — |

这是常见对应关系，不是强制表；以标准和 OEM 规范为准，并在测试里固化。

## 8. 测试用例清单

- 0x22：单 DID、多 DID、顺序、重复 DID、奇数长度、超过最大个数、未知 DID、会话不允许、需要安全且未解锁、多 DID 中混入未知 DID（两种策略）、响应超缓冲、变长 DID、功能寻址。
- 0x2E：固定长度过短 / 过长、只读 DID、会话不允许、安全不满足、取值越界、NVM 写失败（0x72）、异步写（先 0x78 再最终响应）、写后读回、动态 DID 作为目标。
- 权限：读写分别配置；会话切换后安全重新锁定；多 DID 里一个需要安全。
- 0x2C：定义、读取、清除单个和全部、超过上限、源 DID 不可读、地址溢出、重复定义。
- 通用：请求处理中收到新请求；S3 超时后再请求。

## 9. 对你贴的那篇文章：需要谨慎的几处

1. 文章把「多 DID 请求必须先验证全部再返回、任何一个不满足就负响应」说成标准要求。标准明确的是 0x31 的触发条件（例如全部不支持、超过最大个数），部分不支持时的处理是各 OEM 的策略，应做成配置而不是写死。
2. 0x2C 清除子功能里「使用规定的 DID 值清除所有」的说法不够准确，常见做法是省略 DDDID 表示清除全部，请对照你们使用的版本。
3. 文章的写回调示例用 `return 1` 表示成功，而内核里 NRC 以 0 表示无错的风格更常见，建议你自己的回调返回值约定统一一种。
4. 文章里的 `read_session_mask` 用 `uint8_t`，最多只能表示 8 个会话；如果你的会话编号可能超过 8，或者打算支持 OEM 自定义会话，位宽要预留。
5. 文章没有区分「DID 在当前会话不支持」与「服务在当前会话不支持」的 NRC，两者应该分开（第 1 节）。
6. 文章里的区间、DID 示例含义以标准为准；其中「0x0000–0xFFFF 都可用」不代表这些值都能自由分配，有保留区间。

## 10. 下一步
